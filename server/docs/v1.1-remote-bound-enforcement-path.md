# v1.1 Remote-Bound Privacy Enforcement: First Enforced Path

This is the v1.1 record of the *first* outbound path the local privacy engine
defends. Subsequent paths land later (v1.2 mobile, v1.3 federation, runtime
interception, MCP-tool-call wrapping). Until those land, every other path is
explicitly unenforced. This document names the one path that is.

## Chosen path

**Sanctuary ProxyRouter outbound**: every proxied call flowing through
`server/src/proxy/proxy-router.ts` to a configured upstream MCP server.

When the proxy router is constructed with `privacyEnforcement` set, every
proxied tool call routes through `LocalPrivacyEngine.filterOutbound` AFTER
injection detection, context gating, and governor checks, but BEFORE the
upstream forward in `callWithTimeout`.

## Why this path first

1. **Existing real chokepoint.** ProxyRouter is the only place in
   `server/src/` where Sanctuary forwards user-provided arguments to a
   process outside the fortress. Native `sanctuary/*` tools never leave the
   server boundary; only proxied calls do.
2. **Operator-visible.** Upstream servers are configured by the operator in
   the sovereignty profile and surface in the dashboard Fortress View. The
   privacy decision lands in the same operator-facing audit surface.
3. **Lowest architectural risk.** ProxyRouter already chains
   injection -> context-gate -> governor -> forward -> audit. Adding a
   privacy step is a new link in an existing chain, not a new chain.
4. **One file write surface.** Primary edit lives in `proxy-router.ts`.
   `UpstreamServer` gains three optional fields (`destination_category`,
   `privacy_policy_id`, `privacy_identity_id`). Privacy core and contracts
   are imports only.
5. **Composes cleanly with later paths.** The same engine and resolver
   pattern can be lifted into the wrap-time agent-side enforcement
   (Prompt 9), federation outbound (v1.3), and runtime interception
   (post-v1.x). v1.1 proves the shape; later paths reuse it.

## Where the integration sits

```
proxy/proxy-router.ts -> createHandler(serverName, toolName)
  Step 1: injection detection
  Step 2: context gating
  Step 3: governor check (rate, volume, duplicate, lifetime)
  Step 3.5: v1.1 privacy enforcement   <- new
  Step 4: forward to upstream server
  Step 5: governor.recordResult
  Step 6: audit allowed call
  Step 7: v1.1 rehydration of response  <- new
```

## Outbound semantics

- **Allowed:** payload goes through unchanged. Privacy event of kind
  `allowed` is emitted by the engine; the proxy adds its existing allowed
  audit entry.
- **Filtered:** filtered payload (with placeholders) is forwarded; the
  caller-visible audit-chain captures the filter decision via the engine's
  emitted `filtered` event. Raw values never leave the fortress.
- **Denied:** call short-circuits. Caller receives the same generic
  `Operation not permitted` shape the proxy returns for every other denial
  class. A dedicated `proxy_privacy_denied:<tool>` audit entry is appended
  alongside the engine's `denied` event so the dashboard can correlate.

## Inbound (response) semantics

If the outbound was filtered AND a policy is bound, the proxy calls
`engine.rehydrateResponse` on the upstream response:

- **Rehydrated:** placeholders in the response are replaced with the original
  values from the placeholder vault. Caller sees raw values restored.
- **Denied (rehydration):** placeholders remain in the response. Caller sees
  the response as the upstream returned it. The engine emits its own
  `denied` rehydration audit event.

If the outbound was unfiltered or no policy is bound, the response is
passed through with no rehydration attempt.

## Fail-closed behavior

The engine itself enforces fail-closed semantics; the proxy surface honors
those decisions:

- Missing policy (`policyResolver` returns null) -> engine -> denied with
  `fail_closed_no_policy`.
- Policy resolver throws (vault unavailable, decrypt failure, etc.) -> proxy
  catches and treats as no-policy -> engine -> denied with
  `fail_closed_no_policy`. The thrown error is not surfaced in the audit
  metadata to avoid leaking vault details.
- Privacy filter raises during outbound filtering -> engine -> denied with
  `fail_closed_filter_error` or `fail_closed_vault_error`.
- Operator-explicit override on the policy
  (`operator_override.allow_on_*`) flips a denial back to allowed at the
  engine layer. Default (no override) is fail closed.

## Operator override

Override is a *per-policy* operator decision, set on the bound
`PrivacyPolicy`:

```jsonc
{
  "operator_override": {
    "allow_on_policy_error": false,
    "allow_on_filter_error": false,
    "allow_on_vault_error": false,
    "allow_on_detector_error": false
  }
}
```

Default-absent means fail closed. Setting any flag to `true` is a deliberate
operator decision that the engine emits an `allowed` audit event for so it
remains visible. The proxy surface does not introduce a separate override
mechanism.

## Audit safety

Proxy router does not log raw outbound content in any of its own audit
entries (existing convention). Privacy decisions are emitted by the engine
with safe metadata only: detector class, content hash, sanitized field
path, placeholder label. The proxy adds:

- `proxy_privacy_denied:<tool>` on engine denial: server name, tool name,
  tier, denial reason class, latency. No payload, no hashes of raw values.

## Outbound paths NOT enforced at v1.1

These are deliberately out of scope and carry no privacy-engine integration
in this PR:

| Path | v1.x status |
| --- | --- |
| Native `sanctuary/*` tools | Stays in-fortress; no enforcement needed. |
| Webhook approval channel (`principal-policy/webhook.ts`) | Operator-config endpoint; payload is approval metadata, not agent state. v1.x backlog if scope expands. |
| Mesh outbound (`mesh/libp2p-transport`) | Federation-internal; v1.3 hardens privacy at the federation boundary. |
| Concordia / Verascore composition | Default-off, external. Privacy hardening lives in those repositories per the implementation-lane rule. |
| Wrap-time / agent-side enforcement (e.g., agents that call providers directly without going through the proxy) | Prompt 9 wrap-time interception. Same engine + resolver pattern applies. |
| MCP tool calls that an agent harness routes outside Sanctuary's proxy | Out of reach until the harness adopts the wrap. Documented for the v1.1 GA pilot brief. |
| Runtime interception (LD_PRELOAD / network namespacing) | Post-v1.x. Re-evaluate after wrap-time path proves out. |

This list is the v1.1 GA truth-in-advertising surface. Operator briefing
documents repeat it so pilot operators know what is and is not enforced
between Sanctuary and the network.

## Configuration shape

`UpstreamServer` (in `server/src/sovereignty-profile.ts`) gains three
optional fields:

```ts
destination_category?: PrivacyDestinationCategory;  // default "tool-api"
privacy_policy_id?: string;                          // bound policy id
privacy_identity_id?: string;                        // identity for the policy
```

`ProxyRouterOptions.privacyEnforcement` carries the engine and a
`policyResolver` callback. The resolver looks up the policy bound to the
server (using `privacy_policy_id` and `privacy_identity_id` from the
server config). The proxy router does not own the policy store; it
consumes a resolver callback so the wiring is testable in isolation.
