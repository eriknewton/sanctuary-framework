# Audit Log Architecture

## 1. Architecture Summary

Sanctuary's current local audit log is a per-fortress append-only set of individually encrypted audit-entry files. Each entry is JSON, encrypted with AES-256-GCM under the HKDF purpose key `audit-log`, and stored in the fortress state namespace `_audit`. Individual audit entries are not signed and the local audit log is not a Merkle chain. Tamper resistance comes from AES-GCM authentication under a fortress-master-derived key plus the requirement that the operator unlock the fortress to read or rewrite valid entries. This differs from the v1.x federation audit-batch path, which signs and chains batches at the mesh layer.

## 2. On-Disk Layout

The default fortress storage path is `~/.sanctuary`, overridable with `SANCTUARY_STORAGE_PATH` or the wrap `--fortress` path. Runtime code constructs the storage backend at `<storage_path>/state`, so local audit files live at:

```text
<storage_path>/state/_audit/<timestamp-ms>-<counter>.enc
```

For the default path, that is `~/.sanctuary/state/_audit/*.enc`. The deployment guide explicitly notes that `~/.sanctuary/audit/` is obsolete and does not exist on a running deployment.

The file name key is generated by `AuditLog.persistEntry()` as `${Date.now()}-${counter++}`. The storage backend writes that key as `<key>.enc` under the `_audit` namespace. `_audit` is preserved as a literal directory name by the filesystem storage encoder. Each file contains a JSON-serialized `EncryptedPayload`, not plaintext audit JSON. The decrypted plaintext inside that payload is a single `AuditEntry` JSON object with `timestamp`, `layer`, `operation`, `identity_id`, `result`, and optional `details`.

Retention is local and prune-based. `AuditLog` defaults to retaining at most 100 MB or 100,000 files, deleting the oldest timestamp-keyed files first when limits are exceeded.

## 3. Encryption Shape

The master key is derived from the fortress passphrase with Argon2id in `core/key-derivation.ts`. The stored key-derivation parameters live in `_meta/key-params`; recovery-key flows can also provide a raw 32-byte master key. The mantle binding passphrase itself is resolved from `SANCTUARY_PASSPHRASE`, macOS Keychain, or an encrypted fallback `passphrase.enc` file, but that passphrase storage is separate from audit-entry encryption.

The audit encryption key is:

```text
HKDF-SHA256(
  ikm  = masterKey,
  salt = "sanctuary-purpose-v1",
  info = "audit-log",
  len  = 32
)
```

`AuditLog` derives this with `derivePurposeKey(masterKey, "audit-log")`. Each audit entry is encrypted with `encrypt(serializedEntry, auditKey)`, which uses AES-256-GCM with a fresh 12-byte IV. The encrypted payload stores `v`, `alg`, `iv`, `ct`, and `ts`; the GCM tag is included in the encoded ciphertext by `@noble/ciphers`.

No additional authenticated data is supplied on the current audit-entry encryption path. The fortress binding is therefore by storage path, passphrase-derived master key, and `_audit` namespace, not by an explicit fortress identifier in AES-GCM AAD. A ciphertext moved to another fortress will only decrypt if that fortress has the same master key and audit purpose key.

This shape is operator-sovereign in the local fortress sense: the audit log remains unreadable without the unlocked fortress key material, and no per-entry signing ceremony is required for ordinary local audit writes.

## 4. Append Semantics

`AuditLog.append()` constructs an in-memory `AuditEntry`, pushes it into the process-local `entries` array, and starts an asynchronous `persistEntry()` write. The public append API returns `void`; durability is tracked through `pendingWrites`. Short-lived callers must call `flush()` before process exit, and the source comments call out the historical failure mode where CLI processes exited before audit writes reached disk.

Persistence is per-entry, not decrypt-modify-re-encrypt of a whole log. `persistEntry()` serializes one entry, encrypts it independently, and writes one `.enc` file in `_audit`. After the write, it runs `maybeRotate()` as part of the same tracked promise.

The current concurrency model is best-effort single-process append. There is no cross-process lock, no file lock, and no durable monotonic sequence counter. Filename uniqueness comes from `Date.now()` plus an in-process counter. Rotation has a process-local `rotationInFlight` boolean to avoid overlapping prune passes in one `AuditLog` instance.

Crash recovery is entry-granular. A completed `.enc` file is independently decryptable and authenticated. A missing file means the append did not persist. A partially written or corrupted file is skipped by `loadPersistedEntries()` because decryption or JSON parsing fails. The storage backend uses `writeFile`; there is no explicit temp-file rename, write-ahead log, or `fsync` call in the audit path.

## 5. Read And Query Semantics

`AuditLog.query()` first calls `loadPersistedEntries()`. That method lists every file in `_audit`, reads each `EncryptedPayload`, decrypts it with the audit purpose key, parses the plaintext JSON, deduplicates by `(timestamp, operation, identity_id)`, and then sorts the in-memory array by timestamp.

Filtering is in memory. The supported filters are `since`, `layer`, `operation_type`, and `limit`; `limit` defaults to 50 and returns the most recent matching entries. There is no on-disk index. Query cost is therefore linear in retained audit-file count on a cold read, bounded by the retention limits.

Operator-facing read paths use this same API. The `monitor_audit_log` MCP tool calls `AuditLog.query()` directly. The `audit_export_siem` tool also queries the audit log, then applies additional export filters and formats results as CEF or OCSF. Broker-specific `secrets audit` opens the same fortress storage and queries broker operation entries through the L3 broker wrapper.

Exit-bundle import does not add recovered audit receipts to `_audit`. The
exported `artifacts/audit_receipts.json` file is a signed-manifest-pinned
archive artifact with `recovery_semantics: "archive_only"` and
`normal_audit_query_continuity: false`. On import it is staged under
`_exit_audit_receipts` for inspection, so normal audit queries on the
destination only return entries written by that destination fortress.

## 6. Tamper Model

The local audit log resists offline tampering by an attacker who can edit files but does not have the fortress master key. Modifying an existing `.enc` file or inventing a new one without the audit key causes AES-GCM authentication failure, and `loadPersistedEntries()` skips the corrupted file.

The local audit log does not, by itself, provide append-only proof against an attacker who has the master key. Such an attacker can decrypt entries, rewrite history, delete files, and re-encrypt valid payloads. It also does not detect deletion of old valid files, rollback to an older complete `_audit` directory, or concurrent writer races. There is no per-entry signature, no Merkle root, and no durable sequence chain in `AuditLog`.

Plain filenames expose timing metadata because keys are timestamp-prefixed. Multi-fortress correlation from directory names and modification times is therefore outside the encryption boundary.

Castle Wall Phase 1 complements this model at the egress boundary. It is not an audit-log cryptographic proof system; it reduces the chance that encrypted audit blobs or unlocked data leave the machine without operator authorization. A master key from another fortress does not decrypt this fortress's audit entries unless the key material matches.

## 7. PQ Migration Implications

The v1.4 migration hinge for the local `AuditLog` is not per-entry signing. Future build threads should not plan an ML-DSA or Dilithium migration for local audit entries because local entries are not signed today.

The current local chain is symmetric:

- Argon2id derives the 32-byte master key from the fortress passphrase.
- HKDF-SHA256 derives the `audit-log` purpose key.
- AES-256-GCM encrypts each entry.

HKDF-SHA256 and AES-256-GCM remain the relevant symmetric primitives in the post-quantum threat model. The more sensitive migration surfaces are passphrase strength and KDF parameters, envelope versioning for encrypted payloads, and any future asymmetric wrapping layer added around fortress-master material. If the mantle binding later introduces asymmetric master-key wrapping, that wrapping layer is where ML-KEM-768 belongs. It is not an audit-entry migration and should not be implemented as local audit-entry signatures.

Because the current encrypted payload schema has `v: 1` and `alg: "aes-256-gcm"` but no key-wrap metadata, a crypto-agility pass should design explicit envelope metadata before changing algorithms or adding KEM-wrapped key material.

## 8. Comparison To V1.x Federation Envelope Signing

The federation protocol is a separate audit surface. `server/docs/federation-protocol-v0.1-spec.md` section 5 defines canonical audit nodes, streamed audit batches, per-node signatures, HMAC chain proofs, and previous-batch hash continuity. In that path, wire events and audit batches are signed by per-node keys and verified against the fortress-master-anchored trust chain.

Local `AuditLog` does not use that federation envelope format. It writes encrypted local entries through the storage backend. The federation path has a signature-scheme and batch-chain migration problem; the local audit log has a passphrase, HKDF purpose-key, AES-GCM envelope, retention, and storage-integrity problem.

## 9. Operator-Facing Implications

The audit log is unreadable while the fortress is locked because reads require the same master key used to derive the audit purpose key. Unlock through the normal passphrase path, recovery key path, or guardian recovery cascade restores access to the encrypted entries as long as the recovered master key matches the key used to write them.

Operators should inspect the log through `monitor_audit_log`, `audit_export_siem`, dashboard views that bind an unlocked `AuditLog`, or purpose-specific CLIs such as `secrets audit`. Direct `cat` or `grep` of `_audit/*.enc` only shows encrypted payload JSON.

Retention is operator-policy-driven only through `AuditLogConfig` at construction today; defaults are 100 MB and 100,000 entries. Existing multi-tenancy documentation states that cross-tenant or cross-fortress audit aggregation is not performed by the multi-agent dashboard. Each fortress storage path owns its own `_audit` namespace and master-key-derived audit key.

## 10. Open Questions And Future Work

- Explicit AAD binding: local audit entries currently pass no AES-GCM AAD. A future envelope could bind `fortress_id`, namespace, and key into authentication.
- Durability: `writeFile` is used without a temp-file rename or `fsync`. A hardening pass should decide whether audit writes need crash-consistent atomic replacement semantics.
- Cross-process contention: filename uniqueness and rotation coordination are process-local. Multiple writers against the same `_audit` namespace are unsupported in practice but not locked out at the storage layer.
- Rollback and deletion evidence: deletion or rollback of whole valid `.enc` files is not cryptographically detected by the local log.
- Memory hygiene: the audit purpose key is held in the `AuditLog` instance as `encryptionKey`; zeroization on fortress lock or shutdown is not implemented in this class.
- Corruption visibility: query currently skips corrupted entries silently. Operator-visible corruption counters or alerts would improve forensic usability.
- Envelope agility: encrypted payloads expose algorithm and version, but no KDF parameters, key id, fortress id, or wrapping metadata for future PQ or rotation migrations.
