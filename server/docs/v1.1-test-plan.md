# Sanctuary v1.1 Test Plan

Targeted test plan by workstream for the v1.1 Local Sovereignty Harness. Each section names the test files an implementation thread is expected to deliver and the test names that prove the workstream's acceptance criteria from `v1.1-acceptance-checklist.md`. Integration checkpoints span workstreams.

v1.1 scope is local-only, single-operator. Tests below cover one fortress on one operator's machine. Cross-fortress, fleet, and public-federation behavior is out of scope and explicitly enumerated at the end of this document.

Workstream owners run targeted Vitest files during development. The full `npm test` gate runs at integration checkpoints and before merge. Baseline updates land only when the full suite confirms the new count.

## Conventions

- All TypeScript test files live under `server/test/` and follow the existing layout convention (one subdirectory per subsystem).
- Real-crypto tests use the same `@noble/curves` and `@noble/ciphers` primitives as production. They MUST NOT mock the crypto layer.
- Mock-only tests are limited to integration boundaries that depend on environment-specific behavior (filesystem race conditions, OS keychain interaction, network sockets).
- Every test file gets a one-line header comment naming the workstream and the contract surface it exercises.

## Workstream 1: Query Privacy Core (Prompt 3)

Write scope: `server/src/privacy/**`, `server/test/privacy/**`.

### Test files

- `server/test/privacy/detector.test.ts`: recursive bounded sensitive-span detection.
- `server/test/privacy/placeholder-vault.test.ts`: encrypted vault round-trips.
- `server/test/privacy/policy-binding.test.ts`: identity-bound privacy policies.
- `server/test/privacy/rehydration.test.ts`: policy-bound rehydration.
- `server/test/privacy/audit-events.test.ts`: privacy-event emission shape.
- `server/test/privacy/safe-metadata.test.ts`: assertion that no raw sensitive content appears in any emitted event.

### Required test names

- `detector.test.ts`: nested object depth limit, payload size limit, secret-shaped string detection, person/client/project/credential/account/file-path/domain-term coverage, custom detector class, empty input, deeply recursive input.
- `placeholder-vault.test.ts`: stable mapping across two writes of identical input, ciphertext round-trip, vault file is encrypted at rest, missing entry surfaces as unresolvable, vault read fails closed when key derivation fails.
- `policy-binding.test.ts`: identity binding enforced, switching identities switches policies, deny-rule fires correctly, allow-rule passes through, fail-closed on missing policy.
- `rehydration.test.ts`: rehydration permitted by policy succeeds, rehydration denied by policy returns the placeholder, partial rehydration when some entries are missing, rehydration is opt-in per identity.
- `audit-events.test.ts`: filtered, allowed, denied, error, rehydrated payload kinds emit with the v1.1 `PrivacyAuditPayload` shape; the enclosing audit-chain entry that carries each payload verifies under `signature_scheme: "ed25519-v1"`.
- `safe-metadata.test.ts`: no raw sensitive content appears in any field of any emitted privacy event across a representative sample of inputs.

### Crypto

Real-crypto for `placeholder-vault.test.ts` (AES-256-GCM round-trip, HKDF derivation). Mock-only is acceptable for `detector.test.ts` since detection is a pure function over input strings.

## Workstream 4: Internal Coordination (Prompt 6)

### Test files

- `server/test/coordination/policy-gating.test.ts`: context transfer respects policy + privacy gates.
- `server/test/coordination/two-agent-workflow.test.ts`: end-to-end two-agent local workflow with audit chain.

### Required test names

- `handoff-create.test.ts`: Layer 1 sender signature on `LocalHandoffRecord` verifies; canonical JSON is byte-stable; `signature_scheme: "ed25519-v1"` present on the record; sender and recipient identities are scoped to the same fortress.
- `handoff-lifecycle.test.ts`: every transition emits a `LocalHandoffAuditPayload` carried inside an enclosing audit-chain entry; the per-transition signer rule holds (created → sender, accepted → recipient, denied → recipient or policy_gate, completed → recipient, failed → whichever side surfaced the failure); `actor_id` and `signer_role` are populated; the enclosing audit entry's signature attests `actor_id`; invalid transitions are rejected; reason class is recorded for denied and failed.
- `policy-gating.test.ts`: handoff blocked when policy denies the recipient; placeholder vault refs resolve through the privacy filter; raw context not transferred.
- `two-agent-workflow.test.ts`: Agent A delegates to Agent B; full audit chain reconstructed from handoff records; no public federation is invoked.

### Crypto

Real-crypto required across all four files (Ed25519 signing on handoff records is load-bearing).

## Contract-lock test coverage (Workstream 0 follow-up, required before Prompt 3-9 spawn)

Five test files MUST exist before any v1.1 implementation thread spawns. They are deliberately small, deterministic, and live in `server/test/contracts/v1.1/**`. Failure of any of them is a release blocker.

- `server/test/contracts/v1.1/destination-category-sync.test.ts`: asserts that `PRIVACY_DESTINATION_CATEGORIES` from `server/src/contracts/v1.1/constants.ts` matches `ProviderCategory` from `server/src/l2-operational/context-gate.ts` exactly (same set, same hyphen form). Drift between the two layers is a release blocker.
- `server/test/contracts/v1.1/signed-payload-coverage.test.ts`: asserts that every signed envelope type in `server/src/contracts/v1.1/` carries `signature_scheme` inside its signed-bytes contract: `LocalHandoffRecord`, `LocalHandoffAuditPayload`, `ExitBundleManifestBody` (whose `signature_scheme` field is what the wrapper signature commits to). Programmatic check against the type definitions plus a fixture that round-trips canonicalize → sign → verify and demonstrates that scheme-substitution breaks signature verification.
- `server/test/contracts/v1.1/safe-metadata-hardening.test.ts`: dictionary-attack and field-path tests for `PrivacyFieldDecision`. Confirms (a) plain SHA-256 of low-entropy values like "Acme Corp" is collidable against a known dictionary, (b) the keyed `hmac-sha256-fortress-keyed-v1` resists the same dictionary attack with overwhelming probability, (c) `field_path` values that fail `PRIVACY_FIELD_PATH_PATTERN` are rejected at emit time, (d) sensitive object keys are never present in any emitted privacy event across a representative payload corpus.
- `server/test/contracts/v1.1/exit-bundle-path-safety.test.ts`: exhaustive rejection tests for `ExitBundleArtifactEntry.path`: absolute paths, `..` segments (including URL-encoded, double-encoded, Unicode-normalized), backslashes, null bytes, duplicate paths within a manifest, paths whose realpath escapes the extraction root, archive entries that are symlinks or hardlinks, paths longer than `EXIT_BUNDLE_PATH_MAX_BYTES`. Each rejection MUST surface the matching `failure_class` enum value, not a generic error.
- `server/test/contracts/v1.1/harness-readme-parity.test.ts`: asserts that every harness named in `README.md` as a wrap target appears either in `LocalHarnessKind` (first-class) or is documented as flowing through `generic_mcp` (with the README line and the documentation cross-reference both checked). Catches drift between marketing surface and registry shape.

These tests are owned by the coordinator (Prompt 0 follow-up), not by an implementation workstream. They land before Prompt 3 spawns; failure forces a contract amendment, not implementation churn.

## Out of scope

The following do not have v1.1 test coverage. They will be planned alongside their respective release lines.

- Mobile companion (v1.2): planning per Prompt 11; no implementation tests in v1.1.
- Public federation (v1.3): planning per Prompt 12; no implementation tests in v1.1.
- Fleet, payments, compliance packs, advanced cryptographic migration (v1.4+): no v1.1 test coverage.
- Concordia and Verascore composition is default-off and external. v1.1 tests MUST NOT take a hard dependency on either.
