# Sanctuary v1.1 Acceptance Checklist

Operator-perspective gate criteria for the v1.1 Local Sovereignty Harness.

This document is the testable expansion of the four-pillar acceptance gate in `ROADMAP.md` v1.1. Every bullet is a pass/fail check that can be executed against a running fortress with two or three wrapped agents. v1.1 ships only when every section below is GREEN against a single operator on a single machine, with no maintainer help, in under 60 minutes total.

Scope: local single-operator. Public federation, fleet, mobile-native runtime, payments, compliance packs, and crypto migration are out of scope and tracked separately for v1.2 / v1.3 / v1.4+.

## How to use this checklist

Each pillar has the same shape:

- **Pre-conditions**: what must be true before the drill starts.
- **Operator actions**: concrete steps the operator runs.
- **Pass criteria**: what must hold for that pillar to count as GREEN.
- **Out of scope**: surfaces explicitly deferred so reviewers do not chase them.

Reviewer marks each line PASS / FAIL / N-A and records evidence (audit-event id, screenshot, CLI output hash) inline.

## Pillar 1: Query Privacy And Anonymized Query Mode

### Pre-conditions

- [ ] Fortress wrapped over at least one Tier B agent.
- [ ] Privacy policy loaded and bound to the operator identity.
- [ ] Placeholder vault exists, encrypted under the Cognitive layer.
- [ ] At least one remote-bound enforcement path is registered with the fortress.

### Operator actions

- [ ] Operator sends a query containing: a person name, a project name, a client name, a credential-shaped string, and a file path.
- [ ] Operator inspects the dashboard privacy panel after the query.
- [ ] Operator inspects the audit event for the outbound call.
- [ ] Operator examines the placeholder vault contents directly through the operator surface.

### Pass criteria

- [ ] Remote-bound payload contains stable placeholders (`PERSON_1`, `PROJECT_1`, `CLIENT_1`, `SECRET_1`, file-path placeholder) and zero raw sensitive spans.
- [ ] Local placeholder vault entries are encrypted at rest; reading the file directly yields ciphertext.
- [ ] Identical inputs produce identical placeholder labels across two consecutive runs (stable mapping).
- [ ] Recursive nested payloads are filtered to the documented depth and size limits.
- [ ] Response rehydration happens only when the bound policy permits, and the operator can disable rehydration per identity.
- [ ] Audit event contains: detector class, field path, action taken, content hash, policy id, destination category. No raw sensitive content appears in any audit field.
- [ ] Dashboard privacy panel attributes the decision to a specific policy id and shows safe metadata only.
- [ ] If the privacy policy fails to load or the filter throws, outbound traffic fails closed unless the operator has an explicit override on file.

### Out of scope

- Provider-side anonymization guarantees, traffic-analysis defenses, unlinkability across sessions, network-level metadata protection. Product copy uses "query minimization" or "pseudonymization" where precision matters.

## Pillar 2: Operator-Agent Communication And Control

### Pre-conditions

- [ ] Two or three wrapped agents available across at least two harnesses (where the harness compatibility matrix supports more than one).
- [ ] Local hub APIs running.
- [ ] Audit log healthy with recent entries.

### Operator actions

- [ ] Operator opens the dashboard inbox.
- [ ] Operator approves one Tier 1 action and denies one Tier 2 action through the inbox.
- [ ] Operator changes the policy template on one wrapped agent.
- [ ] Operator pauses, resumes, and lockdowns one wrapped agent through the dashboard.
- [ ] Operator sends a chat or command to a wrapped agent through the dashboard.
- [ ] Operator inspects the activity feed for the actions above.
- [ ] Operator inspects the per-agent budget and policy summary.

### Pass criteria

- [ ] Inbox contains entries for: pending approvals, blocked egress, privacy events, budget warnings, recovery prompts, agent errors.
- [ ] Agent registry shows status, model and provider, policy id, budget summary, and last-activity timestamp for every wrapped agent on the machine.
- [ ] Pause, resume, restart, unwrap, lockdown, and template assignment operations succeed for capabilities supported by the underlying harness.
- [ ] Activity feed entries are backed by audit events and survive a fortress restart.
- [ ] Policy and budget summaries reflect the current bound policy after a policy change.
- [ ] Tier 1 approval gates remain in force from the dashboard. The dashboard never auto-approves Tier 1 work.
- [ ] No secrets, passphrases, private keys, or raw sensitive query content are visible in any inbox card, activity feed item, or summary panel.

### Out of scope

- Cross-fortress hub behavior, fleet-wide views, and any control surface that requires public federation.

## Pillar 3: Internal Agent Coordination

### Pre-conditions

- [ ] Two wrapped agents on the same fortress.
- [ ] Coordination policy permitting the chosen handoff.
- [ ] Audit log healthy.

### Operator actions

- [ ] Operator initiates a local two-agent workflow where Agent A delegates a task to Agent B.
- [ ] Operator inspects the signed handoff record.
- [ ] Operator inspects the audit chain for the handoff and its outcome.
- [ ] Operator denies a follow-up handoff request from Agent B back to a third agent that violates the coordination policy.

### Pass criteria

- [ ] The handoff record carries: sender id, recipient id, task scope, policy context reference, audit reference, and an Ed25519 signature over canonical JSON.
- [ ] Every `LocalHandoffRecord` carries Layer 1 sender signature with `signature_scheme: "ed25519-v1"`. Every lifecycle-transition payload is enclosed in an audit-chain entry that verifies under the same scheme; `actor_id` and `signer_role` follow the per-transition signer rule.
- [ ] Context transfer between agents is filtered by the active policy and privacy gates.
- [ ] Audit entries exist for: handoff created, handoff accepted, handoff denied, handoff completed, handoff failed (where applicable).
- [ ] The denied handoff is logged with a generic denial reason and does not reveal which policy rule fired.
- [ ] No public federation, cross-operator discovery, or external relay is invoked at any point in the workflow.
- [ ] The workflow completes without Concordia or Verascore being required.

### Out of scope

- Public agent pools, cross-fortress discovery, reputation exchange across fortresses, anonymized-want broadcasting, multi-operator coordination.

## Pillar 4: Portability And Exit

### Pre-conditions

- [ ] Source machine has a wrapped Sanctuary agent with at least one identity, recent audit entries, and at least one reputation attestation.
- [ ] Destination machine has Node.js and npm.
- [ ] Operator has the source passphrase or recovery material.

### Operator actions

- [ ] Operator runs a single export command that produces a `SANCTUARY_EXIT_BUNDLE_V1`.
- [ ] Operator transfers the bundle to the destination through their own approved channel.
- [ ] Operator runs the standalone verifier CLI against the bundle.
- [ ] Operator runs the import command on the destination, observes the verify-before-activate stage, and resolves any conflicts.
- [ ] Operator wraps the destination harness.
- [ ] Operator opens the destination dashboard and inspects identity, audit continuity, reputation evidence, policy continuity, and placeholder-vault metadata continuity.
- [ ] Operator triggers a re-keying flow on the imported encrypted state.

### Pass criteria

- [ ] One command produces a complete bundle. Operator does not need to chain `state_export`, `reputation_export`, and `sanctuary_export_identity_bundle` manually.
- [ ] The manifest enumerates every artifact, lists per-artifact hashes, and records identity binding plus version metadata.
- [ ] No private key or passphrase appears in the bundle.
- [ ] The verifier CLI runs offline, requires no network access, and validates manifest hashes plus signature chains.
- [ ] Import refuses to activate on hash or signature failure and reports the failure at the artifact level.
- [ ] Imported attestations whose source identity cannot be verified are marked unverifiable, not silently trusted.
- [ ] After re-keying, the operator can read imported state without the original passphrase.
- [ ] After wrap on the destination, the dashboard shows full identity, audit, reputation, policy, and placeholder-vault continuity. The source platform is no longer required.
- [ ] Every irreversible action (export, import activation, re-keying, unwrap) traversed a Tier 1 approval.
- [ ] The full drill is recorded as signed audit events on both source and destination.

### Out of scope

- Cross-operator transfer, hardware key transfer, managed TEE migration, third-party verifier UX polish.

## End-to-End Drill

### Pre-conditions

- [ ] Pillars 1 through 4 all GREEN in isolation.
- [ ] Single operator, single source machine, single destination machine, no maintainer help.
- [ ] Fresh dashboard session on each machine.

### Operator actions (single 60-minute window)

- [ ] Wrap two or three agents on the source machine.
- [ ] Communicate with each agent from the dashboard.
- [ ] Run a local multi-agent workflow.
- [ ] Send at least one outbound query through the privacy filter.
- [ ] Approve, deny, pause, resume, and lockdown agents from the dashboard.
- [ ] Inspect audit and privacy events end-to-end.
- [ ] Export the durable record, verify the bundle on the destination, import, re-key, and wrap on the destination.
- [ ] Confirm the destination operates without the source platform.

### Pass criteria

- [ ] The above completes in under 60 minutes.
- [ ] No CLI fallback was required at any step where the dashboard is supposed to handle the action.
- [ ] No secrets, passphrases, private keys, or raw sensitive query content are visible to the operator at any point in the drill.
- [ ] The audit chain on the destination machine connects back to the source machine through verifiable signatures.
- [ ] Every signed artifact (handoff record, exit-bundle manifest, mesh-batch envelope) carries `signature_scheme: "ed25519-v1"`. Every payload that is not a signed envelope (privacy events, hub activity feed entries, local agent registry records, handoff lifecycle transitions) is enclosed by an audit-chain entry that verifies under the same scheme.

### Out of scope

- Mobile companion control, public-federation interactions, fleet workflows, payment rails, compliance pack generation.

## Acceptance hand-off

When every section above is GREEN, the v1.1 release is acceptance-cleared. Any FAIL line is a release blocker; any N-A line must be justified inline (typically tied to a harness that does not implement the underlying capability). The acceptance reviewer signs the bottom of this document with date and audit-event id when the drill completes.

Authority for changes to this checklist: coordinator only, through dated amendments to the v1.1 scope-lock document.

## Automated drill suite

The four pillars are backed by automated integration drills under `server/test/drills/`:

- Pillar 1: `v1.1-privacy-drill.test.ts`
- Pillar 2: `v1.1-hub-drill.test.ts`
- Pillar 3: `v1.1-coordination-drill.test.ts`
- Pillar 4: `v1.1-exit-drill.test.ts`

The drills exercise real `MemoryStorage`, real `AuditLog`, real Ed25519 signing, real http servers + `handleHubRoute`, and the operator-facing `sanctuary exit verify` CLI. They are the gating proof that v1.1 implementation has converged before the v1.1.0 release tag.

The drills are integration tests, not pilot-operator manual scripts. The pilot-operator <60-minute end-to-end stand-up drill remains a separate manual gate captured by this document.
