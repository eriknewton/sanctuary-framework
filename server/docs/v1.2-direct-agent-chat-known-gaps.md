# v1.2 Direct-Agent Chat, Known Gaps and Operator Workflow

**Status:** v1.2.0 ships PR #96 (operator side), PR #97 (F9, wrapped-agent reply hook), PR #98 (click-to-chat session-open polish), and the F10 follow-up (Path 2 CLAUDE.md augmentation for Claude Code, plus cross-harness operator chat setup docs).

This document explains what works end-to-end in v1.2.x, the known gaps, and how operators bridge them today.

## What v1.2.x ships end-to-end

- **Operator side (PR #96):** chat surface in dashboard, Tier 1 approval gate for session-open, encrypted chat history at `_chat/agent.<agent_id>`, audit emission on every operator message and agent reply.
- **Wrapped-agent side (PR #97 / F9):** standalone `sanctuary chat-server` MCP subprocess advertising `chat/poll_inbox` + `chat/send_reply`, encrypted session-record persistence at `_chat/session.<id>`, per-agent active-session index for O(1) lookup, cross-agent isolation guard.
- **Click-to-chat (PR #98):** clicking the wrapped-agent tile opens the chat surface directly without the redundant Tier 1 confirmation modal. Session open still emits the audit event.
- **Wrap CLI:** `sanctuary wrap` registers `sanctuary-chat` as a sibling MCP server in the harness config alongside `sanctuary`, so the wrapped agent's runtime can invoke the chat tools.
- **Path 2 augmentation (F10):** `sanctuary wrap --claude-code --install-hooks` (default-on) appends a Sanctuary-tagged section to `~/.claude/CLAUDE.md` that tells Claude Code to voluntarily call `chat/poll_inbox` after every turn. Claude reads the augmentation as operator-supplied context and replies via `chat/send_reply` on its own initiative.
- **Dashboard:** polls direct-agent history every 2s while a chat surface is mounted; renders agent replies inline within ~2s of arrival.

## The autonomous-poll gap

F9 ships the MCP TOOL CONTRACT for replies. The wrapped agent's RUNTIME LOOP that calls those tools is harness-level behavior, not an MCP-server behavior. Claude Code, OpenClaw, Cline, and the rest do not have a built-in "background poll Sanctuary every 5 seconds" loop. Agents call MCP tools when their model decides to, not on a timer.

This means: in v1.2.x, sending a message in the dashboard does not automatically trigger the wrapped agent to reply unless the agent's runtime has been instructed to poll. F10 closes that gap for Claude Code via the CLAUDE.md augmentation; cross-harness operators close it manually with the per-harness snippet in `server/docs/operator-chat-setup.md`.

## Paths in v1.2.x

### Path 1: Operator-prompted (v1.2.x baseline)

The operator prompts their wrapped agent (in whatever interface that agent runs in: Claude Code CLI, OpenClaw chat, etc.):

> Check `chat/poll_inbox`. If there are any operator messages, respond via `chat/send_reply`.

The agent's runtime calls `chat/poll_inbox`, sees the queued operator messages, composes a reply, and calls `chat/send_reply`. The dashboard's 2s polling timer renders the reply within ~2s of the tool call returning.

**Cost:** zero infrastructure. **Friction:** operator runs a manual prompt per round-trip.

This is the v1.2.x baseline. Use this to verify F9 is wired up correctly end-to-end.

### Path 2: CLAUDE.md augmentation (v1.2.0 default for `--claude-code` wraps)

**SHIPPED in v1.2.0 via `sanctuary wrap --install-hooks` (default-on for `--claude-code`).** The wrap CLI appends a Sanctuary-tagged fenced section to `~/.claude/CLAUDE.md`. Claude Code reads `~/.claude/CLAUDE.md` on session start as user-global instruction context. The augmentation describes the `sanctuary-chat` MCP tools and tells Claude to call them voluntarily after every turn. Claude treats the instruction as operator-supplied context (the trusted shape) rather than mid-stream injection. The trust model mirrors the broker-server pattern that has worked since v0.10.0: Sanctuary exposes tools, the agent voluntarily calls them.

Operator-side latency: ~3-5 seconds from a dashboard message to the rendered reply when Claude is in or just-finished a turn. For a Claude session sitting idle at the prompt with no active turn, type any character in the harness; the next turn reads the inbox and replies.

**Idempotent:** the augmentation section is delimited by exact fenced HTML comment markers (`<!-- SANCTUARY:CHAT-AUGMENTATION-V1 -->` and the matching close). Re-running `sanctuary wrap --install-hooks` against a CLAUDE.md that already contains the V1 marker is a true no-op. Operator content above and below the section is preserved byte-for-byte. A pre-write backup at `~/.claude/CLAUDE.md.sanctuary-backup` snapshots the prior file on every modify-existing install.

**Multi-fortress:** the augmentation body is invariant across wraps. Per-fortress binding lives in the `sanctuary-chat` MCP-config env block (`SANCTUARY_AGENT_ID`, `SANCTUARY_FORTRESS_PATH`), not in CLAUDE.md. The most-recent wrap binds `sanctuary-chat` to the most-recent fortress; CLAUDE.md remains stable.

**Coexistence:** other operator content in CLAUDE.md (style preferences, project-specific instructions, prior augmentations) is preserved. The Sanctuary section is appended to the end with a single blank-line separator above it.

**Opt-out:** `sanctuary wrap --claude-code --no-install-hooks` skips the augmentation install. Use the per-harness system-prompt augmentation in `server/docs/operator-chat-setup.md` as the manual fallback.

For non-Claude-Code harnesses, paste the per-harness augmentation snippet from `server/docs/operator-chat-setup.md` into your harness's persistent system-prompt surface (Cline custom-instructions, `.cursorrules`, OpenClaw skill, Hermes system prompt, Mastra agent instructions). Manual install for now; auto-install for those harnesses is a v1.2.x or v1.3 follow-up.

### Retired approach: Stop-hook-as-delivery (PR #99)

Initial F10 design used the Claude Code Stop hook with `decision: "block"` plus `reason: "<operator message>; reply via tool X"` to inject pending messages between turns. Field testing 2026-04-30 confirmed Claude's safety training correctly classifies the injection-shape payload as a prompt-injection attempt and refuses. This is not a bug in the safety training; it is a design-level mismatch between F10's mechanism and Anthropic's safety posture.

The CLAUDE.md augmentation approach (Path 2 above) works WITH safety training rather than against it. The agent reads the augmentation as operator-supplied context on session start, then voluntarily polls the inbox using the trusted MCP tool. Same operator-perceived UX (round-trip closes on the agent's own turn boundary; idle Claude needs one keystroke), simpler trust model, uniform with the cross-harness augmentation pattern.

PR #99 was closed in favor of the Path 2 reshape; the Stop-hook installer code never landed on `main`.

### Path 3: MCP push notifications (v1.3 work)

Wire `notifications/list_changed` so the chat-server pushes when new operator messages land, instead of waiting for the agent to poll. The wrapped agent's MCP runtime would receive a notification and the agent's loop would observe it on the next turn.

Deferred to v1.3 because harness support varies. Claude Code declares the schema but does not register a handler (anthropics/claude-code#13646). Cline's `resource-list-changed` implementation is broken (cline/cline#1394). Cursor lacks support (open feature request). OpenClaw, Hermes, and Mastra status not authoritatively confirmed for the v1.2 search window. When Claude Code, Cline, and Cursor all close their respective issues, v1.3 can land push notifications and deprecate the polling timer.

**Cost:** spec work + per-harness compatibility testing. **Friction:** none after harness support lands.

## Operator workflow recommendations

| Setup | Use this path |
|---|---|
| You're verifying chat works end-to-end (drill, debug, demo) | Path 1 |
| You're using Claude Code as your daily harness | Path 2 (default; `sanctuary wrap --claude-code` installs the augmentation) |
| You're using Cline / Cursor / OpenClaw / Hermes / Mastra | Path 2; per-harness setup snippets in `server/docs/operator-chat-setup.md` |
| You're running a multi-agent fleet and want zero-friction replies | Path 2 (every harness has a persistent-system-prompt surface) |
| Cross-fortress federation chat | Wait for v1.4 federation surface |

## Why this is documented and not a bug

Sanctuary's MCP-server contract is intentionally minimal. F9 ships the tools. How the agent runtime decides to call those tools is the agent's concern (and the operator's, via system-prompt config). This separation is what lets F9 work with every harness that speaks MCP today, not just the ones with a hypothetical built-in polling loop.

The autonomous-feeling chat experience operators may expect from messaging apps requires either Path 2 (agent-side instruction; shipped in v1.2.0 for Claude Code) or Path 3 (server-side push; v1.3). Both are real engineering work, sequenced deliberately, not gaps in F9 itself.
