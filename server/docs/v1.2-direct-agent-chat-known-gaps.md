# v1.2 Direct-Agent Chat — Known Gaps + Operator Workflow

**Status:** v1.2.x ships in PR #96 (operator side) + PR #97 (F9, wrapped-agent reply hook).

This document explains what works end-to-end in v1.2.x, the known gaps, and how operators bridge them today.

## What v1.2.x ships end-to-end

- **Operator side (PR #96):** chat surface in dashboard, Tier 1 approval gate for session-open, encrypted chat history at `_chat/agent.<agent_id>`, audit emission on every operator message + agent reply.
- **Wrapped-agent side (PR #97 / F9):** standalone `sanctuary chat-server` MCP subprocess advertising `chat/poll_inbox` + `chat/send_reply`, encrypted session-record persistence at `_chat/session.<id>`, per-agent active-session index for O(1) lookup, cross-agent isolation guard.
- **Wrap CLI:** `sanctuary wrap` registers `sanctuary-chat` as a sibling MCP server in the harness config alongside `sanctuary`, so the wrapped agent's runtime can invoke the chat tools.
- **Dashboard:** polls direct-agent history every 2s while a chat surface is mounted; renders agent replies inline within ~2s of arrival.

## The autonomous-poll gap

F9 ships the MCP TOOL CONTRACT for replies. The wrapped agent's RUNTIME LOOP that calls those tools is harness-level behavior, not an MCP-server behavior. Claude Code, OpenClaw, Cline, etc. don't have a built-in "background poll Sanctuary every 5 seconds" loop — agents call MCP tools when their model decides to, not on a timer.

This means: in v1.2.x, sending a message in the dashboard doesn't automatically trigger the wrapped agent to reply. Each round-trip currently requires either the operator or the agent's own task-context to invoke `chat/poll_inbox`.

## Three paths to bridge the gap

### Path 1 — Operator-prompted (v1.2.x default)

The operator prompts their wrapped agent (in whatever interface that agent runs in: Claude Code CLI, OpenClaw chat, etc.):

> Check `chat/poll_inbox`. If there are any operator messages, respond via `chat/send_reply`.

The agent's runtime calls `chat/poll_inbox`, sees the queued operator messages, composes a reply, and calls `chat/send_reply`. The dashboard's 2s polling timer renders the reply within ~2s of the tool call returning.

**Cost:** zero infrastructure. **Friction:** operator runs a manual prompt per round-trip.

This is the v1.2.x baseline. Use this to verify F9 is wired up correctly end-to-end.

### Path 2 — System-prompt augmentation (v1.2.x optional, harness-level)

For lower-friction replies, add to the harness's system prompt or persistent memory file (e.g. `~/.claude/CLAUDE.md` for Claude Code, equivalent for other harnesses):

```
You are operating inside Sanctuary Framework. You have an operator
chat inbox at MCP tool chat/poll_inbox. At the start of every turn,
before doing anything else, call chat/poll_inbox. If it returns
operator messages, respond to them via chat/send_reply before
continuing your current task.
```

The agent now polls every turn. Latency = one agent turn (~2-5s for Claude Code). Operator types a message, gets a reply on the agent's next turn.

**Cost:** one-time CLAUDE.md edit. **Friction:** none after setup.

This is harness configuration, not Sanctuary-server code. F9 doesn't ship it because it's per-operator, per-harness, per-deployment. Operators who want autonomous-feeling chat add this to their harness setup.

### Path 3 — MCP push notifications (v1.3 work)

Wire `notifications/list_changed` so the chat-server pushes when new operator messages land, instead of waiting for the agent to poll. The wrapped agent's MCP runtime would receive a notification and the agent's loop would observe it on the next turn.

This was rejected for v1.2.x in F9's spawn prompt because harness support varies (Claude Code, Cline, OpenClaw all have different states of `notifications/list_changed` adoption). When the harness ecosystem stabilizes around it, v1.3 can land push notifications and deprecate the polling timer.

**Cost:** spec work + per-harness compatibility testing. **Friction:** none after harness support lands.

## Operator workflow recommendations

| Setup | Use this path |
|---|---|
| You're verifying F9 works end-to-end (drill, debug, demo) | Path 1 |
| You're using direct-agent chat regularly with one wrapped agent | Path 2 |
| You're running a multi-agent fleet and want zero-friction replies | Path 2 (per agent harness) |
| Cross-fortress federation chat | Wait for v1.3 push notifications |

## Why this is documented and not a bug

Sanctuary's MCP-server contract is intentionally minimal. F9 ships *the tools*. How the agent runtime decides to call those tools is the agent's concern (and the operator's, via system-prompt config). This separation is what lets F9 work with every harness that speaks MCP today, not just the ones with a hypothetical built-in polling loop.

The autonomous-feeling chat experience operators may expect from messaging apps requires either Path 2 (agent-side instruction) or Path 3 (server-side push) — both are real engineering work, deferred deliberately, not gaps in F9 itself.
