# Synthetic Coverage Harness

This directory contains the v1.3 synthetic fixture coverage harness for the Sanctuary assurance matrix.

The harness is the substrate for GA gate (a). It turns fixture execution into three artifacts:

- Per-platform coverage reports for Linux and macOS.
- A cross-platform parity report that confirms both platforms saw the same rows, fixtures, and outcomes.
- A gate (a) rollup artifact that converts coverage and parity into the release gate verdict.

## Layout

- `assurance-matrix.ts` loads the repository root `ASSURANCE_MATRIX.md` file and turns its 20 table rows into typed objects.
- `registry.ts` exposes the fixture registry used by later PRs. PR 1 intentionally leaves it empty.
- `report.ts` joins assurance rows to registered fixtures and renders JSON plus Markdown output.
- `run.ts` is the command entrypoint used locally and in GitHub Actions.
- `parity.ts` compares Linux and macOS coverage reports.
- `rollup.ts` produces the final gate (a) artifact from Linux coverage, macOS coverage, and parity.
- `test/` contains Vitest coverage for the parser, empty registry behavior, and report shape.
- `.out/` is generated by the harness and is ignored by git.

## Running

From the repository root:

```bash
npm run synthetic-coverage
```

The command writes:

- `scripts/synthetic-coverage/.out/report.json`
- `scripts/synthetic-coverage/.out/report.md`

The Markdown report is also printed to stdout.

To compare two platform reports:

```bash
npm run synthetic-coverage:parity -- \
  artifacts/ubuntu/report.json \
  artifacts/macos/report.json
```

The parity command writes:

- `scripts/synthetic-coverage/.out/parity.json`
- `scripts/synthetic-coverage/.out/parity.md`

To produce the GA gate (a) artifact:

```bash
npm run synthetic-coverage:gate-a -- \
  artifacts/ubuntu/report.json \
  artifacts/macos/report.json \
  scripts/synthetic-coverage/.out/parity.json
```

The gate command writes:

- `scripts/synthetic-coverage/.out/gate-a-artifact.json`
- `scripts/synthetic-coverage/.out/gate-a-artifact.md`

It exits non-zero when the gate state is `gate_a_red`.

## Fixture Campaign

PRs 2 through 4 add fixture modules that call `registerFixture(...)`.

Each fixture maps to an `ASSURANCE_MATRIX.md` row by stable row ID. The current matrix does not carry a numeric ID column, so this harness assigns IDs `1` through `20` in table order.

Fixture modules should register side effects before `buildReport(...)` runs. The intended pattern is to import fixture modules at the top of `run.ts`:

```ts
import "./fixtures/substrate-trust-path.js";
```

PR 5 adds cross-platform parity verification.

PR 6 adds the final coverage rollup that produces the v1.3 GA gate (a) artifact.

## Report Semantics

Rows with no registered fixture are marked `no_fixture`.

Rows with at least one fixture and no failures are marked `covered`.

Rows with any failing fixture are marked `partial`.

The per-platform report is informational by itself. The gate decision is made only after Linux coverage, macOS coverage, and parity have been composed by the rollup.

## Gate (a) Semantics

The gate (a) artifact contains:

- `claim_to_row`: every assurance row with Linux and macOS fixture counts and coverage state.
- `gap_inventory`: every known coverage gap, including whether it blocks the gate.
- `version_matrix`: the Sanctuary SHA and fixture totals for each platform.
- `gate_violations`: blocking failures that keep the gate red.
- `gate_state`: `gate_a_green` or `gate_a_red`.

Rows marked `proven` in `ASSURANCE_MATRIX.md` must have at least one fixture on both Linux and macOS. A proven row with zero fixtures on either platform produces a `proven_without_fixture` violation.

Rows marked `partial` or `planned` do not block the gate only because they lack fixtures. They still appear in `gap_inventory` so release reviewers can see the remaining work.

Parity is always blocking. If the parity report is `diverged` or `incomplete`, the rollup creates a `parity_divergence` violation for each affected row.

`gate_a_green` means all proven rows are fixture-backed on both supported platforms and the parity report is clean. This is the v1.3 GA gate (a) evidence.

`gate_a_red` means the artifact is still useful: it names the exact rows that need fixture work or matrix reclassification before the gate can close green.

## Release Verification

The canonical gate (a) evidence for a release is the `synthetic-coverage-gate-a` artifact from the GitHub Actions run on the release tag or the merge commit used for that release.

Operators can verify gate (a) themselves by checking out the release tag, installing server dependencies, and running the same harness commands used by CI:

```bash
git checkout v1.3.0
cd server && npm ci && cd ..
npm run synthetic-coverage
```

CI runs that command on Linux and macOS, then runs parity and the gate rollup. A local single-platform run proves only the current platform report. The release artifact proves the full cross-platform gate.

## Adding Fixtures

Fixture names must be stable. Registering the same fixture name for the same claim ID dedupes to one fixture.

Fixture functions return:

```ts
{
  passed: boolean;
  message?: string;
  durationMs: number;
}
```

Keep fixture output deterministic where possible. Expensive or platform-specific drills should make the platform assumption explicit in their registration module.
