# Synthetic Coverage Harness

This directory contains the v1.3 synthetic fixture coverage harness for the Sanctuary assurance matrix.

The harness is the substrate for GA gate (a). PR 1 creates the parser, registry, report shape, and CI workflow. Later PRs add the actual fixture generators and final gate behavior.

## Layout

- `assurance-matrix.ts` loads the repository root `ASSURANCE_MATRIX.md` file and turns its 20 table rows into typed objects.
- `registry.ts` exposes the fixture registry used by later PRs. PR 1 intentionally leaves it empty.
- `report.ts` joins assurance rows to registered fixtures and renders JSON plus Markdown output.
- `run.ts` is the command entrypoint used locally and in GitHub Actions.
- `test/` contains Vitest coverage for the parser, empty registry behavior, and report shape.
- `.out/` is generated by the harness and is ignored by git.

## Running

From the repository root:

```bash
npm run synthetic-coverage
```

The command writes:

- `scripts/synthetic-coverage/.out/report.json`
- `scripts/synthetic-coverage/.out/report.md`

The Markdown report is also printed to stdout.

## Fixture Campaign

PRs 2 through 4 add fixture modules that call `registerFixture(...)`.

Each fixture maps to an `ASSURANCE_MATRIX.md` row by stable row ID. The current matrix does not carry a numeric ID column, so this harness assigns IDs `1` through `20` in table order.

Fixture modules should register side effects before `buildReport(...)` runs. The intended pattern is to import fixture modules at the top of `run.ts`:

```ts
import "./fixtures/substrate-trust-path.js";
```

PR 5 adds cross-platform parity verification.

PR 6 adds the final coverage rollup and closes v1.3 GA gate (a).

## Report Semantics

Rows with no registered fixture are marked `no_fixture`.

Rows with at least one fixture and no failures are marked `covered`.

Rows with any failing fixture are marked `partial`.

PR 1 treats the report as informational. The empty registry is expected, and all 20 rows should report `no_fixture`.

## Adding Fixtures

Fixture names must be stable. Registering the same fixture name for the same claim ID dedupes to one fixture.

Fixture functions return:

```ts
{
  passed: boolean;
  message?: string;
  durationMs: number;
}
```

Keep fixture output deterministic where possible. Expensive or platform-specific drills should make the platform assumption explicit in their registration module.
