# v1.9.0-rc.3 (2026-11-05)

This opt-in release candidate is published on npm's `next` channel. The stable
`latest` channel remains v1.8.4 until 1.9.0 ships. rc.3 adds the wall
reliability, Hermes memory, console and warehouse work merged since rc.2. No
claim below goes beyond the bounded rows of the
[Assurance Matrix](../../ASSURANCE_MATRIX.md). The full list is in
[CHANGELOG.md](../../CHANGELOG.md).

```bash
npm install -g @sanctuary-framework/mcp-server@1.9.0-rc.3
```

The public prerelease is
[`v1.9.0-rc.3`](https://github.com/eriknewton/sanctuary-framework/releases/tag/v1.9.0-rc.3).

## What changed since rc.2

### Wall reliability (macOS Castle Wall and the audit log)

- **System traffic is summarized, not logged flow by flow (macOS).** The Castle Wall daemon counts root-owned flows and writes one summary record per audit heartbeat instead of one record per flow. Agent flows are recorded exactly as before, and root traffic feeds no liveness, posture or armed-banner evidence.
- **The full daemon can run under launchd (macOS).** `sanctuary castle-wall install-full`, `uninstall-full`, `full-status` and `reset-full` manage the full Castle Wall daemon as a user-session LaunchAgent. launchd restarts it after a crash, and a crash-loop counter stops automatic restarts once the daemon keeps failing, so a broken configuration cannot spin forever. All four commands need an attended terminal; `uninstall-full` and `reset-full` also need `--yes`; running two of them at once is unsupported. No restart or reboot drill is recorded for this path yet, so rc.3 claims no drilled restart behavior, and the proven macOS enforcement row in the Assurance Matrix is unchanged by it.
- **Audit appends cost less on a large log.** Each append lists the log once by name instead of inspecting every file, retention pruning keeps a small margin below the cap, and pruning advances one authenticated step at a time within a bounded episode. Measured on Linux, an append on a log of one hundred thousand entries went from seconds to a fraction of a second. Entry encryption, the chain and the anchor formats are unchanged.
- **Flushes are durability barriers.** A hot-path audit flush returns only after the entries it covers are on disk, checkpoint work is spread across flushes, and when several writers share one log a writer does not re-checkpoint what another writer already covered. Checkpoint verification reads several checkpoint bodies at once under a fixed concurrency while still deciding in checkpoint order. The tamper-evident audit chain row stays `partial` in the Assurance Matrix.
- **Audit locks and writers are stricter.** Recovering the audit write lock after its holder dies requires proof that the holder is gone; a lock that cannot be proven gone is left in place and reported for operator recovery. Audit chains admit a writer by the role it declares and by who owns the chain's directory, and diagnostic readers (`doctor`, the Castle Wall observe and safe-mode paths, the evidence-pack readers) leave lock files as they found them. Lock teardown belongs to the holder that still has the lock. Lock recovery is tested on Linux; the macOS runtime check is still owed.
- **Audit discovery states its outcome.** Opening an audit log reports a typed outcome before it allocates a sequence number. An unknown state stops for operator investigation; an authenticated empty suffix continues from its current sealed boundary.
- **`sanctuary castle-wall` exits cleanly.** The command ends with its own exit code.

### Hermes memory

- **Saving to your own memory does not prompt.** An agent's save into its own memory (`memory_insert`, `sanctuary_remember`) runs without an approval prompt under the default policy, within a bounded save allowance that is shared across processes and restarts. Past the allowance an ordinary Tier 2 approval is requested, and the approval card says why in plain words. Every save is audited with the saving agent named when its identity is known and marked unknown otherwise, and the dashboard's Evidence page shows attempts apart from completed saves. Deletion, export, ingest, emit and provenance operations still ask. Set `memory_save_approval: always` in the principal policy to prompt on every save. Sovereign memory custody stays `partial` (Rung 1 candidate) in the Assurance Matrix; confirming the default on a real wrapped agent is the operator's remaining acceptance step.
- **Hermes can use Sanctuary for memory.** Two Hermes plugins ship in `hermes-plugin/`: a memory provider that saves and recalls through the Sanctuary memory bridge, and a tools plugin that exposes the bridge's tools to the agent. The bridge's second tool catalog serves seven tools: own-memory saves run without a prompt within the allowance, `memory_recall` returns a bounded context of matching saved passages, `sign_statement` and `export_memory` answer that they are not available yet, `protection_rules` is refused, and every refusal is an ordinary tool result. Real Hermes is driven through save, cold recall and teardown in an acceptance test on Linux and macOS; installed acceptance on a real operator host is still owed, so the roadmap does not yet say Hermes runs on Sanctuary by default.
- **One command installs it.** `sanctuary protect --hermes-memory` sets Hermes to save and recall memory through the Sanctuary memory plugin, turns Hermes's built-in memory off and removes the Sanctuary MCP server entry from its config, so memory has one path. `sanctuary protect --hermes-memory --unwrap` reverts those changes and keeps edits the operator made to the Hermes config in the meantime. The installer is safe to interrupt and to run twice.
- **Recover an unfinished save.** If a Hermes memory save is cut short, the bridge refuses to start until the save is recovered, and startup prints the one sentence that says what to run. `sanctuary hermes recover-save --fortress <dir>` reports what it found and changes nothing; with `--apply` it rolls back an unpublished save or keeps a verified one, clears the save intent and writes an audit entry. It refuses when the save cannot be classified or the bridge is still running against that fortress, and it is safe to repeat.

### Dashboard and posture

- **Approval cards say what is asked, how long is left and why a decision missed.** With the dashboard as the approval channel, a held request shows a short bounded preview of what is asked (how many bytes, which namespace or identity, and for a memory the text it would save), shown on the operator's dashboard only. A countdown follows the server's deadline and the controls disable when it runs out; a late click gets a plain answer: expired, already decided, or no longer exists. Tier 1 consent is two readable steps. After a server restart the live stream reconnects with a bounded backoff, and the page says the server restarted only when it did. The agent sees nothing new, and denials still give no reason. Live refresh stays `partial` in the Assurance Matrix.
- **The posture home stays up when one source is slow.** Each panel runs under its own time budget. A panel that misses its budget shows its last known value marked stale, or an honest "unavailable" with the reason, while the rest of the page stays current; a stale panel never renders green, and an unavailable agents roster reads Unknown rather than zero. Audit-chain re-verification reuses results for entries whose bytes have not changed. At ten thousand audit entries the audit-reading panels are measured fresh on macOS; on Linux they can miss their budget and show stale, which is tracked separately.
- **Every protection layer is listed.** `sanctuary_active_protections` and the posture home list every protection layer as on, off, not built or unknown, each with the evidence it rests on. On comes only from a current observation from an existing producer; policy intent and enabled flags never earn it. Missing, stale or unverified evidence reads unknown with the reason, and the tool and the page share one layer inventory and one set of evidence rules. The page passes fewer observations than the tool today, so a layer can read unknown on the page while the tool reads on; input parity lands in a later release.
- **A refused lockdown lift says why (macOS).** When an approved lockdown lift is refused, the dashboard shows a short reason from a fixed list instead of a generic failure. A lift is refused on any platform where stopping an agent is unsupported, matching the stop, and a refused lift leaves the stop snapshot and the agent's locked-down status untouched. Per-agent network stop stays `partial` in the Assurance Matrix.
- **Blocked-egress records are ready for their card; the card stays empty.** Castle Wall blocked-egress records now carry a bounded destination and the producer's verification state, a verified record vouches only for the fields the producer signed, and the inbox's blocked-egress store is capped per origin, deduplicated and expiring. No shipped path writes these records to the inbox yet, so the blocked-egress card stays empty, as do the privacy and recovery cards; budget-warning cards stay empty for the reason given in the rc.2 notes.

### Sovereign Data Warehouse

- **Write-journal groundwork.** The record format, signing contract, generation guards and ordered admission for the warehouse write journal are defined and tested. Nothing in production calls them yet, so no warehouse behavior changes in this release; the journal engine is a later slice.
- **A refused import leaves a row.** An SDW import refused for an empty or non-string source key reference now leaves a denial row in the audit log, like the other refusals the import handler makes before approval.

### Security

- Audit record integrity hardening; a notice with affected and fixed versions follows under the coordinated-disclosure terms in SECURITY.md.

No signed macOS app is attached to this preview yet; the v1.8.4 app does not pair with it. CI and test-only changes carry no notes line. Everything else in the rc.2 and rc.1 notes below still applies.

# v1.9.0-rc.2 (2026-10-27)

This opt-in release candidate is published on npm's `next` channel. The stable

The public prerelease is

## What changed since rc.1

- **Approval cards you can read.** With the dashboard as the approval channel, a held Tier 1 request appears as a card that says in plain language what the agent asked for, and the operator's Approve or Deny is what the held call receives. Card text, decision labels, operator token entry and the findings count were reworked since rc.1.
- **A livelier console.** The dashboard's live stream now carries inbox and agent status updates, and while that stream is open and the tab is visible the console also refetches its inbox and agent data about once a minute. Live refresh stays `partial` in the Assurance Matrix; the dashboard does not promise real-time delivery.
- **Restore a locked-down agent (macOS).** On macOS, the operator can give a locked-down agent its network access back from the dashboard, through Tier 1 approval. A second approval of the same restore is refused, so one approval set restores once; a restore that fails leaves the agent locked down and can be tried again.
- **Exports hand over their re-key key once.** A dashboard export that contains encrypted state shows its re-key key once, in the approving dashboard only. If that response is lost, make a new export.
- **Honest empty states.** The inbox can project budget warnings and agent errors from the local agent registry, but no shipped component writes budget caps or an agent error status to it yet. Budget-warning cards therefore stay empty, as do blocked-egress, privacy and recovery cards until their producers carry evidence the card may claim. Agent-error cards from a failed fortress-wide lockdown still appear as before.
- **Audit verification is stricter.** `audit-chain verify` no longer passes an export with unsigned checkpoint records.
- **Quieter automation.** Runs with the `CI` environment variable set no longer open the dashboard in a browser. The MCP SDK dependency is updated to 1.32.0.

No signed macOS app is attached to this preview yet; the v1.8.4 app does not pair with it. Everything else in the rc.1 notes below still applies.

```bash
npm install -g @sanctuary-framework/mcp-server@1.9.0-rc.1
```

The public prerelease is
[`v1.9.0-rc.1`](https://github.com/eriknewton/sanctuary-framework/releases/tag/v1.9.0-rc.1).

## What changed

- **Linux wall, published.** On Ubuntu 24.04 (x86-64), the separately published [Castle Wall Linux 0.1.0-1](https://github.com/eriknewton/sanctuary-framework/releases/tag/castle-wall-linux-0.1.0-1) package enforces a signed operator policy per user account, through five reboots on three fresh servers, and this release's command line signs policies in the `uid-<uid>` scope form that package accepts (`sanctuary-linux-policy-sign`; tested, not drilled) and provides its upgrade command (`sanctuary castle-wall upgrade-linux`). That is the whole claim: one distribution and architecture, literal addresses only, a checksum-verified package with no signature or apt repository yet, no real agent harness tested, and unattended reboot survival is not claimed.
- **Setup an agent or script can finish.** `sanctuary protect --passphrase-stdin` reads the fortress passphrase from piped input, so setup completes without a terminal prompt. A refused `protect` now exits non-zero and says what to do.
- **A smoother first install.** Fixes from the unpublished 1.8.5 and the 1.8.6 previews, which never reached the default channel, are carried here: the fortress opens with the keyring factor `init` enrolled, the recovery key is staged outside the fortress, and a fresh fortress passes `doctor`. Default `init` no longer touches the machine-wide Castle Wall trust anchor; that changes only through a confirmed `sanctuary castle-wall re-pin`.
- **The install planner says what it found.** It reports whether an operator approval path is actually usable, where the staged recovery file is, and whether the vault is provisioned, so an installing agent knows before it acts.
- **Ask the server before you wrap anything.** `sanctuary_help` answers "should I install this", "what are the bounds" and "how do I verify or uninstall" by pointing to read-only posture tools or the exact command.
- **More complete backups and restores.** Full exports and checkpoints include every exportable durable namespace (reserved internal namespaces are not exported); state import and checkpoint restore check version floors before writing anything and accept entries signed before an identity rotation; an interrupted restore or master-key rotation finishes on the next retry. The export and exit guarantee as a whole stays `partial` in the Assurance Matrix.
- **Memory that survives restarts.** Memory handles from `sanctuary_remember` persist across server restarts, and command-line memory ingest works on a fresh store. The command-line memory verbs now need the wrapped agent's `SANCTUARY_AGENT_ID` and apply the same vault owner rule as the server.
- **Verascore publishing asks first.** `reputation_publish` now always requires operator approval, including on installs whose policy file lists it under `tier3_always_allow`, because Sanctuary wrote that line at first setup. No migration step is needed.
- **Two more SIEM formats.** `audit_export_siem` adds `ecs` (Elastic Common Schema) and `xdm` (Cortex XDR) output from the same redacted audit view as `cef` and `ocsf`, with field-mapping references in `integrations/siem/`.
- **A dashboard that fails gracefully.** It starts without waiting on optional requests, labels panels with no live data as unavailable instead of erroring, and a busy dashboard port no longer stops the MCP server: approvals are refused in that session instead.

### Dashboard

The dashboard is now a console, dark by default, with a rail for Overview, Approvals, Agents, Machines, Enforcement, Findings, Evidence and Policies, and Talk as a side panel. On the new screens a value the server does not serve reads Unknown or Not evaluated with its reason, never zero.

- **Overview** shows the Castle Wall arm state, approvals waiting, open Sentinel findings, the audit chain check and how many detected agents have protection requested. Outbound connection counts appear only beside a current, passing audit chain check over a window the server read in full.
- **Approvals** is one queue for Tier 1 and Tier 2 holds with filters and a drawer that says what each request does and why it is held. Tier 1 approval takes two steps. Every decision ends in one kept result (taken, refused or unconfirmed), and decision controls on every screen pause while one is being sent.
- **Agents, Machines, Findings, Policies and Evidence** read served data: an agent detail page with its configured reach, a machine health check that reads Unknown rather than down when a machine does not answer, and an Evidence view of the audit log that states the server's own chain verdict.
- **Talk** keeps a draft and the reader's place through refreshes and between the side panel and the full page.

### Security

- Ed25519 signatures checked through the shared identity verifier must meet a strict profile: non-canonical encodings, small-order points and points outside the prime-order subgroup are refused.
- A state export approved at the Tier 1 gate runs on the namespace set fixed when approval was requested.
- Command-line refusals for an unrecognized option or argument never print the text that was typed, apart from a single-letter short flag.
- Storage resolves each namespace name to one directory and checks stored names before changing anything; exit-bundle and memory-archive files are read through a size-checked, bounded reader.

## Capability bounds

These bounds from earlier releases still stand, and nothing in rc.1 removes them:

- macOS Castle Wall boot survival is proven only for attended reboots on one host and one OS version; unattended reboot survival is not claimed.
- No audited per-rule, per-flow trail is claimed for the wall on macOS or Linux.
- On Linux, only the narrowed Ubuntu 24.04 (x86-64) claim above is proven. Fault injection, other distributions and CPU architectures, hostname and DNS rules, a real agent harness, and any Linux package build other than 0.1.0-1 are not covered.
- Agent wrapping is tested on representative harness paths and is not proven for every harness version.
