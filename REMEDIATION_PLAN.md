## PRE-FLIGHT AUDIT REVIEW

### PRE-FLIGHT CHECK 1: PROMPT INJECTION COVERAGE

These are MCP tools designed to be called by AI agents. Prompt injection — where adversarial content in agent input causes the agent to misuse its tools — is the primary LLM-specific attack surface. SECURITY_AUDIT.md references prompt injection in passing (SEC-001 mentions "a compromised or prompt-injected agent") but does not contain dedicated findings covering the three canonical prompt injection vectors:

**(a) User-controlled input reaching a model prompt without sanitization.** NOT COVERED. Concordia negotiation terms, agent names, want/have descriptions, and session metadata are all user-controlled strings that an agent harness may incorporate into its prompt context. If an agent reads a counterparty's offer text (via `concordia_session_status` or `concordia_relay_receive`) and that text contains adversarial instructions, the agent may be induced to call destructive tools. Neither codebase sanitizes or tags data returned to the agent as "untrusted external content."

**(b) Agent output being passed back into a prompt without sanitization.** NOT COVERED. MCP tool responses are returned to the agent harness, which typically appends them to the conversation context. Sanctuary tool responses include Merkle proofs, attestation content, and SHR reports — all of which could be crafted by a counterparty (via the bridge or handshake) to contain adversarial prompt content. Neither codebase marks response fields as needing sandboxing in the agent context.

**(c) Data crossing the tool boundary being injected into a downstream prompt.** NOT COVERED. The Concordia-to-Sanctuary bridge is the highest-risk path: Concordia negotiation terms (controlled by a counterparty agent) are forwarded to Sanctuary's `bridge_commit`. If the agent harness logs or displays the bridge response, crafted terms could inject instructions into the downstream prompt. The relay system is equally exposed: messages received via `concordia_relay_receive` are counterparty-controlled and returned verbatim.

**SEC-ADDENDUM findings logged:**

**SEC-ADD-01 — Tool Responses Returned to Agent Context Contain Unsanitized Counterparty-Controlled Data**
Severity: High
Affected tools: `concordia_relay_receive`, `concordia_session_status`, `concordia_propose`, `concordia_counter`, `bridge_verify`, `handshake_respond`, `handshake_complete`, `concordia_search_agents`, `concordia_get_want`, `concordia_get_have`
Description: All of these tools return data that was originally supplied by a counterparty agent. The MCP response includes this data as plain strings in the JSON response. An agent harness that appends tool responses to its prompt context will incorporate counterparty-controlled text into its reasoning, enabling indirect prompt injection. This is the standard attack vector for agent-to-agent prompt injection via tool use.
Remediation note: This is partially an agent-harness responsibility, but the MCP servers should (a) document which response fields contain counterparty-controlled data, and (b) consider adding a `_trust_level: "external"` metadata field to responses containing counterparty content, enabling harnesses that support it to apply sandboxing.

**SEC-ADD-02 — Concordia Negotiation Terms Accept Arbitrary Strings With No Content Filtering**
Severity: High
Affected files: `concordia/mcp_server.py` (all negotiation tools), `concordia/session.py`
Description: Negotiation terms, offer content, reasoning text, and message payloads accept arbitrary strings with no length limit enforced at the Concordia layer (FastMCP may impose transport-level limits, but Concordia applies no application-level caps). A counterparty can embed extremely long strings, Unicode control characters, or text formatted as system prompts in any negotiation field. These flow through to `concordia_session_status` responses that the agent harness will process.

**SEC-ADD-03 — Sanctuary Bridge and Handshake Responses Include Counterparty-Supplied Attestation Content**
Severity: High
Affected files: `server/src/bridge/tools.ts`, `server/src/handshake/tools.ts`, `server/src/l4-reputation/tools.ts`
Description: `bridge_verify` returns the full outcome terms (counterparty-controlled). `handshake_complete` returns the counterparty's SHR (counterparty-controlled). `reputation_query` returns attestation metadata that may have been generated by a counterparty. All of these are returned as plain text in MCP responses that the agent harness appends to prompt context.

### PRE-FLIGHT CHECK 2: MEDIUM FINDINGS REVIEW

All Medium findings from SECURITY_AUDIT.md reviewed:

**SEC-004 — Schema Validation Does Not Recurse Into Nested Objects (Medium)**
Summary: `validateArgs()` in `router.ts` checks top-level types but does not recurse into nested object properties. The `terms` argument to `bridge_commit` accepts any nested structure. Deep nesting or large key counts can DoS via `stableStringify` recursion.
Assessment: Denial of service, not data loss or sovereignty violation. **Retain Medium.**

**SEC-006 — bridge_commit Signing Payload Uses Non-Canonical JSON.stringify (Medium)**
Summary: Ed25519 signature over commitment payload uses `JSON.stringify` instead of `stableStringify`. Currently consistent within Sanctuary (both sign and verify use the same path), but not portable across runtimes.
Assessment: Latent portability defect, not currently exploitable. **Retain Medium.**

**SEC-011 — Gate Default for Unlisted Operations Is Tier 3 (Allow) (Medium)**
Summary: New tools added to the MCP server that are not listed in any policy tier default to Tier 3 (auto-allow). A developer adding a sensitive tool without updating the policy creates an unguarded operation.
Assessment: **RECLASSIFY to High.** Justification: The default-allow posture is a systemic sovereignty risk. Sanctuary's security model depends on the gate evaluating every operation — a single missed tool registration creates a permanent bypass for that tool. The safe default must be deny, not allow. This is not a theoretical concern: the codebase has 40+ tools and active development; the probability of a future tool being added without a policy update is high. A missed sensitive tool (e.g., a future `identity_delete` or `state_purge`) would execute without any human approval. This directly violates CLAUDE.md Sovereignty Property #9: "Every tool call is evaluated by the ApprovalGate before execution."

**SEC-012 — Dashboard Authentication Token Passed in Query String (Medium)**
Summary: Dashboard auth token is accepted via `?token=<TOKEN>` query parameter due to SSE EventSource limitations. Tokens appear in URL logs, proxy logs, and browser history. This token can approve or deny any Tier 1 or Tier 2 operation.
Assessment: **RECLASSIFY to High.** Justification: The dashboard token is the highest-privilege credential in the system — it authorizes state export, identity rotation, and reputation import. Exposure via URL logging is a well-known, frequently exploited vulnerability class. Any proxy, CDN, or browser extension that logs URLs captures this token. The attack path is: deploy dashboard behind a reverse proxy → proxy logs URLs → attacker reads logs → attacker approves arbitrary Tier 1 operations. This is a realistic data loss path in any deployment that uses the dashboard behind infrastructure.

**SEC-013 — Webhook Callback Server Has Wildcard CORS (Medium)**
Summary: Webhook callback sets `Access-Control-Allow-Origin: *`. Combined with low-entropy request IDs (32 bits), cross-origin approval brute-forcing is theoretically possible, though HMAC verification mitigates significantly.
Assessment: HMAC makes exploitation impractical. **Retain Medium.**

**SEC-015 — Want/Have Registry Has No Identity Verification (Medium)**
Summary: Any caller can post wants/haves under any agent_id. Market data pollution, not data loss.
Assessment: No data loss or sovereignty violation. **Retain Medium.**

**SEC-017 — Bridge Stores Full Concordia Outcome Including Deal Terms (Medium)**
Summary: `bridgeStore.save()` persists both commitment and full terms. Terms are encrypted but would appear in plaintext in an export bundle. Design tension with Concordia's privacy invariant.
Assessment: Terms are needed for verification. Export is Tier 1 gated. **Retain Medium**, but flag for architectural review.

**SEC-021 — Concordia Exposes Private Key Bytes via KeyPair Methods (Medium)**
Summary: `KeyPair.private_key_bytes()` method exists and is accessible. Not currently called from tool handlers, but no defense-in-depth prevents future misuse.
Assessment: Defensive concern, not currently exploitable. **Retain Medium.**

**Reclassification summary:** SEC-011 and SEC-012 reclassified Medium → High.

### CP-01: Move `state_delete` (with `secure_delete: true`) to Tier 1
**Finding:** SEC-001 (Critical)
**Remediation:** In `server/src/principal-policy/loader.ts`, move `state_delete` from the `tier3_always_allow` list (line ~49) to the `tier1_always_approve` list (lines 37-43). Specifically, add `'state_delete'` to the Tier 1 array. This ensures any deletion — especially irreversible secure deletion — requires human approval. If a non-secure `state_delete` (without `secure_delete: true`) should remain Tier 3, split the tool into two: `state_delete` (Tier 3, soft delete / unlink only) and `state_secure_delete` (Tier 1, 3-pass overwrite). The split is the cleaner fix because it separates the reversible and irreversible operations at the tool level.
**Effort:** Small (< 2 hrs)
**Dependencies:** None.

### CP-02: Remove `auto_deny: false` Option From Webhook and Dashboard Channels
**Finding:** SEC-002 (Critical)
**Remediation:** In `server/src/principal-policy/webhook.ts` (lines 176-183) and `server/src/principal-policy/dashboard.ts` (lines 181-184), remove the `auto_deny` configuration option entirely. ### CP-03: Fix Recovery Key Path to Prompt for Existing Key Instead of Regenerating
**Finding:** SEC-020 (High, but Critical data-loss impact)
**Remediation:** In `server/src/index.ts` lines 98-124, replace the `TODO` block. When a `recovery-key-hash` exists in `_meta` but no passphrase is provided: (1) read the recovery key from an environment variable `SANCTUARY_RECOVERY_KEY` or from stdin, (2) verify it against the stored hash, (3) derive the master key from the recovery key using the same KDF parameters. If neither passphrase nor recovery key is provided, print an error message explaining the two options and exit with a non-zero status. Never generate a new random master key when existing encrypted data is present. Add a startup check: if any `.enc` files exist under the storage path but the master key is freshly generated (not derived from existing credentials), abort with an error — this is a safety net against silent data loss.
**Effort:** Medium (2-8 hrs)
**Dependencies:** None.

### CP-04: Enforce Signature Verification in Concordia Session State Machine
**Finding:** SEC-010 (High)
**Remediation:** In `concordia/session.py`, method `apply_message()` at line ~115: before validating the state transition (line 129), call `verify_signature(message, public_key)` from `signing.py`. The session must hold a reference to each party's public key (already available via `SessionContext.initiator_key.public_key_bytes()` and `responder_key.public_key_bytes()`). If signature verification fails, raise a new `InvalidSignatureError` (do not advance state, do not append to transcript). Also add a call to `verify_signature` inside `validate_chain()` in `message.py:88-105` so that chain validation includes signature checks, not just `prev_hash` chaining.
**Effort:** Medium (2-8 hrs) — requires threading public keys through session context to `apply_message`.
**Dependencies:** None, but coordinates with CP-05 (Concordia auth model).

### CP-05: Add Caller Authentication to Concordia MCP Tools
**Finding:** SEC-007 (Critical)
**Remediation:** This is the largest single fix. Concordia needs a per-call authentication layer. The minimum viable implementation: (1) On session creation (`concordia_open_session`), generate keypairs server-side (as now) and return a session-scoped bearer token (256-bit random, hex-encoded) for each party. (2) All subsequent tool calls for that session must include the bearer token in an `auth_token` parameter. (3) The MCP server validates the token against the session's stored tokens before executing any tool handler. (4) For non-session tools (registry, relay, reputation), require that the caller first calls `concordia_register_agent` which returns an agent-scoped bearer token, and all subsequent calls using that `agent_id` must include the token. This is not full cryptographic authentication (which would require the agent harness to hold a signing key), but it prevents trivial impersonation from a second MCP client. Document clearly that this is transport-level authentication, not cryptographic identity verification.
**Effort:** Large (> 8 hrs) — touches all 46 tools, requires token storage, validation middleware.
**Dependencies:** Must be designed before CP-06, CP-07, CP-08.

In `registry.py:257-259`, check the secret before popping the entry.
**Effort:** Small (< 2 hrs) with CP-05 in place; Medium without.
**Dependencies:** CP-05 (preferred), or standalone interim fix.

### CP-07: Add Ownership Verification to Relay Message Retrieval

### CP-08: Make Attestation Signature Verification Mandatory

### HP-01: Resolve Canonical JSON Serialization Divergence
**Finding:** SEC-003 (High), BUG-007 (Major)
**Remediation:** Adopt a single canonical serialization specification and implement conformance tests that run against both implementations. The specification must define: (a) `ensure_ascii=True` in both implementations (all non-ASCII characters escaped as `\uXXXX`), (b) number formatting: integers as decimal without trailing `.0`, floats using a deterministic algorithm (recommend RFC 8785 / JCS number serialization), (c) `null` for both JS `null`/`undefined` and Python `None`, (d) recursive sorted keys, (e) compact separators `(",",":")`. Concretely: in `concordia/signing.py:70-80`, change `ensure_ascii=False` to `ensure_ascii=True`. In `server/src/bridge/bridge.ts:53-73`, verify that `JSON.stringify` for number values matches the specified format (V8's default is close to JCS but needs explicit testing for edge cases like `1e20`, `-0`, very small floats). Write a shared test vector file (JSON) containing 50+ edge cases (Unicode, large numbers, deeply nested objects, empty strings, null values) and run both serializers against it in CI, comparing byte-for-byte output.
**Effort:** Medium (2-8 hrs) for the fix; additional Medium for the cross-language test suite.
**Dependencies:** None, but must be completed before any bridge integration testing.

## SECTION 3: SYSTEMIC PATTERNS

*Findings that share a root cause. Each pattern gets one architectural fix.*

### PATTERN 1: Cache-Truth Divergence in Sanctuary StateStore

**Findings covered:** BUG-001, BUG-002, and structurally related to the Merkle tree rollback risk (REVIEW_MAP.md §6, known gap #10).

**Root cause:** The `StateStore` in `state-store.ts` maintains in-memory caches (`contentHashes`, version cache) that are populated lazily on read/write and are treated as authoritative for operations that need a complete or accurate picture of persisted state. The caches are never proactively synchronized with disk, and some operations (import skip, fresh session) leave the caches stale.

**Single remediation:** Convert the `StateStore` to a write-through cache architecture:
1. On every `write()`, update the cache AND write to disk atomically (already done).
2. On every `read()`, populate the cache (already done).
3. On `export()`, `import()`, and any operation that needs a complete namespace list, read directly from the storage backend — never rely on cache for completeness. Add `StorageBackend.listNamespaces()` and `StorageBackend.listKeys(namespace)` methods.
4. After `import()` completes (whether entries were written or skipped), invalidate and reload the cache for all affected namespaces by reading from disk.
5. Add an invariant check: if the cache has an entry, it must match disk. Periodically (or on `export`), verify a sample of cache entries against disk and log warnings on mismatch.

**Effort:** Medium (2-8 hrs) as an architectural change; individual fixes in HP-03 and HP-04 address the immediate symptoms.

### PATTERN 2: Bridge Protocol Incompleteness

**Findings covered:** BUG-005, BUG-006, BUG-007, BUG-008, SEC-003, SEC-006, SEC-017.

**Root cause:** The bridge was designed at the type/schema level but never integration-tested with actual data flowing from Concordia to Sanctuary. The two sides were implemented independently with incompatible payload shapes, incompatible serialization, and a field name typo. The bridge is non-functional end-to-end.

**Single remediation:** Treat the bridge as a protocol specification problem. Write a `BRIDGE_PROTOCOL.md` document specifying: (a) the exact payload schema (ConcordiaOutcome fields, types, required/optional), (b) the canonical serialization spec (RFC 8785 / JCS with explicit decisions on all edge cases), (c) the DID convention for Concordia agents, (d) the field name mapping between Concordia message envelopes and bridge payloads. Then implement both sides against this spec, with a cross-language integration test that: creates a Concordia session → drives it to AGREED → generates bridge payload → feeds payload to Sanctuary `bridge_commit` → verifies via `bridge_verify`. This test must pass in CI. Individual fixes (HP-01, HP-06, HP-07) address specific symptoms; this pattern ensures they cohere.

**Effort:** Large (> 8 hrs) for the full protocol spec + cross-language test; Medium if the individual fixes are done first and this is a verification pass.

### PATTERN 3: Missing Verification Calls (Dead Verification Code)

**Findings covered:** SEC-010 (signatures not verified on session apply), SEC-014 (attestation signatures optional), BUG-009 (Sybil closed-loop never triggers), BUG-014 (commitment reveal not marked).

**Root cause:** Verification functions exist and are correctly implemented, but are never called from the operational code path. The codebase has more verification infrastructure than it uses, creating a false sense of security coverage.

**Single remediation:** Audit every `verify_*`, `validate_*`, `check_*`, and `mark_*` function in both codebases. For each, confirm it is called from the operational path — not just from tests or standalone utility functions. Create a "verification call matrix" documenting: function name, where it should be called, where it is actually called. Any function that should be called but isn't is a finding. Specifically: wire `verify_signature()` into `apply_message()` (CP-04), make attestation signature verification mandatory (CP-08), fix the Sybil closed-loop logic (HP-08), and call `markRevealed()` from `proof_reveal` (Section 4 fix). Going forward, add a CI check or code comment convention (`// VERIFIED: called from X`) that makes verification call sites explicit.

**Effort:** Medium (2-8 hrs) for the audit; individual fixes are Small each.

### PATTERN 4: Concordia Has No Caller Authentication

**Findings covered:** SEC-007, SEC-008, SEC-009, SEC-014, SEC-015.

**Root cause:** Concordia was designed as a protocol library, not as a multi-tenant service. Every tool trusts the `agent_id` parameter as the caller's identity. There is no authentication layer between the MCP transport and the tool handlers.

**Single remediation:** CP-05 (add bearer token auth) addresses this pattern at the root. All individual findings (CP-06, CP-07, CP-08, and the want/have registry fix) are downstream of this single architectural change. The implementation order should be: (1) design the token model, (2) implement token issuance and validation middleware, (3) retrofit all 46 tools to require tokens, (4) update tests.

**Effort:** Large (> 8 hrs) — this is the single largest remediation item.

## SECTION 6: WHAT THIS AUDIT COULD NOT SEE

### 1. Prompt Injection at Runtime

The SEC-ADDENDUM findings (SEC-ADD-01/02/03) identify the attack surface, but the actual vulnerability depends on how the agent harness processes MCP tool responses. Static analysis of the MCP server code cannot determine whether the agent harness:
- Appends tool responses verbatim to the prompt context (vulnerable)
- Sandboxes tool responses in a separate context window (mitigated)
- Applies input filtering to tool responses before prompt inclusion (partially mitigated)

**What is needed:** Red-team testing with an actual agent harness (Claude, GPT-4, or equivalent) connected to both MCP servers. The test should: (a) create a Concordia session where one party embeds adversarial instructions in offer terms, (b) observe whether the other party's agent follows those instructions, (c) test whether adversarial content in relay messages, attestation metadata, or SHR reports can cause the agent to call destructive tools (e.g., `state_delete`). This cannot be automated without an LLM in the loop.

### 2. Multi-Session State Attacks

The audit examined individual tool calls and single-session flows. It did not test:
- **Sanctuary baseline manipulation:** An attacker who knows the baseline tracker's algorithm could craft a sequence of sessions that gradually shifts the baseline to normalize anomalous behavior, eventually causing Tier 2 checks to miss genuine attacks.
- **Concordia cross-session reputation gaming:** An attacker who creates many short sessions with varying parameters could find combinations that maximize reputation score while minimizing Sybil flags. The scoring weights are not formally analyzed.
- **Race conditions in concurrent tool calls:** Both MCP servers process tool calls sequentially (stdio transport is serial), but the webhook/dashboard approval channels introduce asynchrony. A race between two Tier 1 operations where approval for operation A is applied to operation B was not tested.

**What is needed:** A stateful fuzzer that drives multi-session sequences and monitors for invariant violations (monotonicity, baseline drift, reputation inflation).

### 3. Supply Chain Risks Beyond CVE Databases

CVE checks confirm no known vulnerabilities in the pinned dependency versions. They cannot detect:
- **hash-wasm WASM binary integrity:** The WASM blob in `hash-wasm` is pre-compiled. Build reproducibility has not been confirmed. A compromised npm publish could include a WASM binary with weakened Argon2id parameters that produces correct-looking output with reduced security. Verification requires building the WASM from the upstream C source and comparing byte-for-byte.
- **MCP SDK behavior under adversarial transport conditions:** The `@modelcontextprotocol/sdk` and Python `mcp` packages handle transport, framing, and message routing. Malformed MCP messages, oversized frames, or partial writes could trigger undefined behavior in the SDK before Sanctuary/Concordia code is reached. The SDK internals were not audited.
- **Transitive dependency risk in Python:** Because Concordia has no lockfile, `pip install` resolves the full dependency tree of `cryptography`, `jsonschema`, and `mcp` — including their transitive dependencies. These transitive dependencies are not enumerated in REVIEW_MAP.md and were not checked for vulnerabilities.

**What is needed:** WASM reproducibility verification for hash-wasm. Lockfile generation for Concordia (H-08) to make the full dependency tree visible. MCP SDK fuzzing is out of scope but should be flagged to the SDK maintainers.

### 4. Timing Side Channels

The audit confirmed constant-time HMAC comparison for webhook signatures (`webhook.ts:92-105`). It did not assess:
- Whether Ed25519 signature verification in `@noble/curves` and Python `cryptography` is constant-time (both libraries claim to be, but this was not independently verified).
- Whether the Argon2id WASM implementation leaks timing information about the passphrase.
- Whether `stableStringify` or `canonical_json` execution time varies with input content in a way that leaks information about encrypted state.

**What is needed:** Timing analysis requires hardware-level measurement or statistical analysis of response times under controlled conditions. This is beyond the scope of a code audit.

### 5. Filesystem-Level Adversary Model

Sanctuary encrypts all state at rest, but the threat model for an attacker with filesystem access is not fully specified. Specific gaps:
- **Metadata leakage:** Directory names, file counts, and file sizes under `~/.sanctuary/state/` are not encrypted. An attacker can determine which namespaces exist, how many entries each contains, and the approximate size of each entry.
- **Version rollback:** An attacker who can replace `~/.sanctuary/state/_meta/` files with stale copies may be able to reset the version counter, defeating monotonicity checks (REVIEW_MAP.md §6, known gap #10).
- **Denial of service:** An attacker who can delete or corrupt `.enc` files causes data loss. Sanctuary has no backup, replication, or integrity-check-on-read mechanism beyond the Merkle proof (which requires the file to be readable).

**What is needed:** A threat model document specifying which filesystem-level attacks Sanctuary aims to defend against and which are out of scope. Without this, the encryption-at-rest guarantee is ambiguous.

### 6. Concordia In-Memory State Under Adversarial Load

Concordia's in-memory stores have size caps, but the behavior under sustained adversarial load was not tested:
- What happens when all 10,000 session slots are filled? Are new sessions rejected cleanly or does the system degrade?
- Can an attacker fill the attestation store (100,000 entries) with low-quality attestations, drowning out legitimate ones?
- Is there a cleanup mechanism for expired sessions, or does an attacker who creates and abandons sessions consume capacity permanently until restart?

**What is needed:** Load testing with adversarial patterns. This requires a test harness, not code inspection.
